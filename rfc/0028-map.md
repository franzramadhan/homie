# 0028: Map

| Status | Date | PR | Release |
|---|---|---|---|
| draft | 2026-10-25 | #121 | - |

> A "Map" page, right after Overview in the navigation: the lab as a small top-down
> pixel village in the style of Harvest Moon. Every enabled integration
> is a building, its state shows on the building, and a character named
> homie walks between them. Walking into a door opens that page.

## Problem

The Overview answers "is everything healthy?" with a grid of cards. It
is dense and correct, but it is the same grid every day and it says
nothing about how the parts relate: guests run on Proxmox, Kubernetes
runs on those guests, Flux feeds Kubernetes, Grafana watches all of it.
A homelab is also a hobby. A map that is pleasant to open, and still
tells the truth at a glance, is a reason to look at the lab more often
and a better first impression on the demo instance.

## Proposal

- **Page.** `/map`, labelled "Map", placed right after "Overview" in
  the navigation. `/` stays the Overview and the first tab, so the
  landing page, links, bookmarks and the "homie" brand link keep
  working; the map is a second view of the same data. A role sees the map when its `pages`
  list `map` (RFC 0016); the demo lists it.
- **One building per enabled component.** Only what the config enables
  is built, in the order of the Overview, on fixed plots of a tile map:

  | Component | Building | Opens |
  |---|---|---|
  | Proxmox (one per instance) | barn, one animal per running guest (capped) | `/infra` |
  | Kubernetes (one per cluster) | greenhouse, one crop row per node | `/workloads` |
  | Flux, Argo CD | water tower piping into the greenhouse | `/gitops` |
  | GitHub workflows | workshop | `/workflows` |
  | Grafana alerts | weather vane on a hill | `/observability` |
  | Logs | library | `/logs` |
  | Security presets | guard post with a dog | `/security` |
  | Tailscale | the road and bridge out of the village | `/tailscale` |
  | Certificates | town hall notice board | `/infra` |
  | Updates | shipping bin | `/updates` |
  | History | diary on the homie's house | `/history` |
  | OpenBao, CloudNativePG | vault, well | their Overview card targets |

  Empty plots become grass, so a small lab is a small, tidy village, not
  a village with holes.
- **State, from the server.** Each building reads the same queries and
  the same server-decided tone (`src/status.rs`) as its Overview card,
  so the map, the Overview and notifications never disagree. No new
  endpoint, no new backend logic. The tone shows on the building and in
  words: a sign above the door with the card's first summary line
  ("3 nodes, 14 guests"), a green flag for ok, a yellow flag and dust
  for warn, a red flag and smoke for bad, closed shutters for quiet
  hours, a grey sign while loading or on error (the error text on the
  sign).
- **Time of day.** The sky follows the browser clock (morning, day,
  dusk, night with lit windows). Quiet hours (RFC 0001) draw the night
  with a moon whatever the clock says.
- **homie, the character.** A 16 x 16 pixel sprite, 4 walk frames per
  direction, drawn in code from a palette array (no image files, no
  sprite sheet to license). A small person in indigo overalls (the
  accent) wearing a cap shaped like a house roof with a chimney, carrying
  a wrench. Idle, homie looks around and taps the wrench. The prototype
  in the PR shows it.
- **Controls.** Arrow keys or WASD walk, Enter or Space at a door opens
  the page; clicking or tapping a building walks homie there and opens
  it. Hovering a building shows its sign. Esc leaves the canvas focus so
  the page stays keyboard navigable.
- **Accessible twin.** The canvas has an `aria-label`, and below it a
  plain list of the same buildings (name, status word, summary, link).
  Screen readers and `prefers-reduced-motion` get the list first and a
  still map (no walking, no smoke, no day cycle).
- **Cost.** One `<canvas>`, `requestAnimationFrame` at most 30 fps,
  paused while the tab is hidden or the canvas is off screen. Pixel art
  is drawn at 1x into an offscreen buffer and scaled with
  `image-rendering: pixelated`. No game engine, no new dependency.
- **Design rules.** The map is the one place where `DESIGN.md` allows
  decorative color: a fixed pixel palette, limited to the canvas. Status
  still uses only the `ok`/`warn`/`bad`/`quiet` tokens (their dark-theme
  values on the canvas, which read on grass in both themes), always
  next to a word. The page chrome, the sign tooltips and the list twin
  follow `DESIGN.md` as usual.

### Configuration

| Key | Default | |
|---|---|---|
| `map.enabled` | `true` | `false`: no page, no nav entry |

A role or the demo instance gets it through `pages` as usual.

### Logs and metrics

None: the map is client-side and reads existing queries, which are
already logged and counted (RFC 0024).

## Alternatives

| Option | Why not |
|---|---|
| Make the map the landing page (`/`) | Changes every existing link and the habit of opening the Overview; can become a later setting (`map.home = true`) if wanted |
| Isometric view | Prettier, but sprites cost four times the art and hit testing gets harder; top-down is what Harvest Moon did |
| Game engine (Phaser, PixiJS, Kaboom) | 300 kB to 1 MB for one tile map and one sprite; the canvas 2D API covers it |
| Image sprite sheet (PNG) | Needs art files and a license line; palette arrays in code are small, diffable and themeable |
| A topology graph (nodes and edges) | Useful, but it is a different feature; the map keeps the Overview's "one place per component" shape |

## Open questions

1. Should a later setting make the map the home page (`map.home`)?
2. One building per instance (two Proxmox barns) or one per kind with a
   counter?
3. Default on, or opt in (`map.enabled = false` by default)?
4. Should homie react to state (sweats at warn, holds an umbrella when
   Grafana fires, sleeps in quiet hours)?
5. Sound: none (proposed), or an opt-in chime when a building turns bad?

## Testing and rollout

- **Tests:** a unit test that the building list follows `meta` (only
  enabled components, the role's `pages`); a test that each building's
  tone equals its Overview card's tone; the `config::tests::examples_load`
  check covers `map.enabled`. The canvas itself is checked by hand and
  by a screenshot in the PR.
- **Rollout:** a minor version; on by default, nothing to do on upgrade.
- **Off switch:** `map.enabled = false`, or leave `map` out of a role's
  `pages`.
